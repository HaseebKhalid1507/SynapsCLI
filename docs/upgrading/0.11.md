# Upgrading from 0.10.2 to 0.11.0

This page is the full version of the CHANGELOG's Upgrade notes. Read it
before you upgrade a daemon, a broker fleet or a crate that depends on
`synaps-engine`.

**After installing, restart the daemon:** run `synaps daemon reload` (or
`synaps daemon stop`), then restart attached TUIs. A 0.10.2 daemon left
running keeps the old behaviour. It ignores the new `auth.account.*`
selection, refreshes tokens outside the new cross-process lock and can't
serve subagent watch/steer. The first reload is still performed by the
0.10.2 image, which doesn't carry running workers, so let running subagents
finish before you reload. Later reloads carry workers across.

The daemon protocol (v3) and the extension protocol (1) are unchanged; new
wire commands are additive.

## Plugins: `secret_env` (breaking)

**A plugin whose manifest `secret_env` requests a newly denied name now fails
to load**, with an error naming the variable. The denylist is now built from
the provider registries, so it covers every provider key Synaps reads
(including `META_API_KEY`, `KIMI_API_KEY`, `HF_TOKEN`, `NVIDIA_API_KEY`,
`TOGETHER_API_KEY`, `LOCAL_API_KEY` and `OPENAI_CODEX_ACCESS_TOKEN`), plus
the AWS key trio and `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY`/`NO_PROXY`.
Inside `SYNAPS_*` a plugin may name only its own override variable for a key
it declares. A `secret_env` entry that is not an upper-case name
(`[A-Z_][A-Z0-9_]*`) is ignored with a warning and never read; the plugin
still loads.

Fix: move the secret to a plugin-specific variable and update the manifest.
See [extensions/secrets.md](../extensions/secrets.md). (#256)

## Daemon and clients

- **Every client of a daemon session can type** (`client_input = shared`,
  the new default). A second terminal, a dashboard or a bridge no longer
  needs `/takeover` to send a prompt, steer or abort. The client that typed
  last is the active one (`/clients` and `synaps daemon sessions` show it);
  `--observe` clients stay read-only. `client_input = exclusive` keeps the
  0.10.2 rule; it is read when the daemon starts. Older clients keep
  working: they are told they own input. (#300)
- **The daemon socket refuses connections from another user, root
  included.** A connection whose peer credentials can't be read is refused
  too. `sudo synaps --attach` no longer reaches your daemon. (#298)
- **`synaps send --session X` exits 1** when X isn't running or refuses the
  event, instead of dropping it in the shared inbox; `--inbox` keeps the old
  drop. A headless `synaps agent` no longer reads the shared inbox: send to
  it with `synaps send --session <agent>`. (#265)

## Providers

- **The `kimi` provider defaults to `kimi-k3.1-pro`** (was
  `kimi-k2.7-code`): Moonshot closes the K2 series to new users from
  2026-10-31. K3.1 Pro is unlocked by Moonshot only after a top-up (minimum
  $1); until then, choose `kimi/kimi-k2.7-code` explicitly. (#281)

## Turn budgets

`turn_budget.<role>.max_provider_rounds`, `max_tool_calls` and
`max_accumulated_tool_result_bytes` now take a number or `unlimited`.

- **Interactive (foreground) turns have no round, tool-call or
  tool-result-byte limit by default.** They used to stop at 128 rounds /
  512 tool calls / 32 MiB of tool results even while making progress. To keep
  a bound, set `turn_budget.foreground.*` to a number. This also covers
  headless `synaps chat`, `synaps rpc`, detached daemon sessions and resumed
  sessions.
- **Unattended turns stay bounded by default:**

  | Role | Rounds | Tool calls | Tool-result bytes |
  |---|---|---|---|
  | `autonomous` (watcher agents) | 24, no renewals | 96 | 8 MiB |
  | `event` (new: turns a session starts itself for inbox messages and subagent completions) | 24, no renewals | 96 | 8 MiB |
  | `worker` (subagents) | 64 × (1 + 2 renewals) = 192 per run | no limit | no limit |

  Each `subagent_start` or `subagent_resume` is a new worker run. Event
  budgets combine with the session's own budget, and the stricter limit wins.
  Use `unlimited` to lift a default, e.g.
  `turn_budget.event.max_provider_rounds = unlimited`.
- **`0` still means "none allowed"**, as in 0.10.2, in every role. It is
  deprecated: config loading warns that `0` will be rejected in a future
  release. If you wrote `0` to forbid something, keep it for now; it still
  works. If you wrote `0` meaning "no limit", change it to `unlimited`.
  `max_elapsed_secs = 0` still means no wall-clock limit.
- Round renewals (`max_round_renewals`) apply only when a round limit is set.
- `max_cost_usd` now binds on every provider, not only the native Anthropic
  transport.

## Memory

- `memory.default_mode` is now applied to every new interactive session when
  `memory.default_mode_confirmed = true`. Before this release the setting was
  read but had no effect. Check your config: `/memory off` still turns it off
  for a single session.
- A session's own `/memory` choice now survives park/unpark and
  `synaps daemon reload`. A `/memory off` made before you upgraded was not
  saved by the old daemon, so the first reload into 0.11.0 starts that
  session in `memory.default_mode` again. Run `/memory off` once more; from
  then on it sticks.

## Context rollover

With `context_management.mode = auto`, a rolled-over successor now aims for
about 100k tokens (min(100k, ⅔ of the pressure band)). Earlier releases kept
more. Tune this with `context_management.target_tokens`. 0.10.2 does not know
that key and warns "unknown key" if it reads the same config.

## Rolling back to 0.10.2

Sessions saved by 0.11.0 can be opened by 0.10.2. With
`context_management.mode = auto`, 0.11.0 records which message started each
turn. It stores that id beside the message in the session files (`t` on
journal records, `_turn_ids` in the snapshot), never inside the message, so
0.10.2 never sends it to a provider. 0.10.2 ignores these fields and can keep
appending to the session. When 0.11.0 opens it again, the earlier turn ids
are back on the same messages and the first save rewrites the snapshot once.
A malformed `_turn_ids` (for example from a hand edit) is dropped with a
warning; the session still loads.

Pre-release builds of 0.11 stored the id inside the message as
`_synaps_turn`. 0.10.2 would send that key to Anthropic and get HTTP 400.
0.11.0 still reads that layout and rewrites the session in the new layout on
its next save. If you must open such a session with 0.10.2 before 0.11.0 has
saved it again, strip the key first:

1. Stop the daemon that owns the session (`synaps daemon stop`, with the same
   `--profile` if you use one). A running owner would overwrite the edit.
2. Find the sessions directory: `~/.synaps-cli/sessions`, or
   `~/.synaps-cli/<profile>/sessions` for a profile. `SYNAPS_BASE_DIR`
   replaces `~/.synaps-cli`.
3. Strip the key from the snapshot and the journal:

```sh
umask 077
cd ~/.synaps-cli/sessions        # or ~/.synaps-cli/<profile>/sessions
for f in <id>.json <id>.journal; do
  [ -f "$f" ] || continue
  jq -c 'walk(if type=="object" then del(._synaps_turn) else . end)' "$f" > "$f.tmp" \
    && mv "$f.tmp" "$f"
done
```

`jq` may re-render numbers (for example `1.0` as `1`); Synaps reads either form.

0.10.2 does not refuse an empty subagent archive (see Subagents), so don't
resume a startup-failure archive with it.

## Profiles

- `--profile` now exits with an error if it can't be applied, instead of
  running under another profile.
- `SYNAPS_PROFILE` now chooses the daemon (socket, sessions, config) for
  `synaps`, `synaps --attach`, `synaps attach` and `synaps daemon …`, the same
  way `--profile` does. With `SYNAPS_PROFILE` exported you will reach that
  profile's daemon, not the default one.
- A client never attaches to a daemon that serves a different profile.

## MCP

`mcp.json` `env` values are now expanded. MCP children start with a cleared
environment, and `${NAME}` forwards a variable from the parent:

- `${NAME}` becomes the value of `NAME`, or **empty** if it isn't set. A
  warning names the unset variable (never a value). Use `${NAME:-fallback}`
  for a default.
- With `shared: true`, and for every daemon-hosted session, the expansion
  uses the **daemon's** environment (the shell that started it), not the
  attaching shell's.
- A literal `${NAME}` that you meant as text now changes meaning. Check your
  `mcp.json`.

## Accounts (new, opt-in)

You can now store several OAuth logins per provider:
`synaps login --provider <p> --account <label>`,
`synaps auth list|use|remove|identify|plan`. Select an account with
`auth.account.<provider> = <label|default|auto>` or with
`SYNAPS_ACCOUNT_<PROVIDER>`. Your existing login is the `default` account and
nothing changes until you select another one. An unknown or invalid selection
fails closed and never falls back to another account.

- An unknown `auth.*` key now warns `unknown key 'auth.X'`, with a suggestion
  when it is close to a real key: `auth.acount.anthropic` suggests
  `auth.account.anthropic`, and a bare `auth.account` suggests
  `auth.account.<provider>`. 0.10.2 ignores `auth.account.*` silently, so a
  config shared with an older binary leaves that binary on the default
  account.
- If you log in with an older binary after upgrading (a rollback, or another
  host sharing `~/.synaps-cli`), the old binary keeps the previous account's
  stored identity on the slot. Run `synaps auth identify --force` afterwards,
  or the duplicate-account check, `auth list` and `auto` may use the stale
  identity. 0.11.0 does not detect this on its own. It could notice that
  another program rewrote the slot's tokens, but not whether that program
  was an old binary logging in to a different account or the same old
  binary doing an ordinary token refresh, so it can't tell when the stored
  identity has become stale.

## Remote broker fleets

- **Upgrade the broker host (`synaps auth-broker`) before the clients.**
  Upgraded clients can only request named accounts from an upgraded broker.
- Against a 0.10.2 broker, `synaps status` (and `status --all`) falls back to
  the broker's old `/usage` endpoint for the default Anthropic account.
  Other accounts, account listing and other providers report "broker is
  older than this client; … unavailable (upgrade the broker host)".
  `synaps quota-keeper` stops with the same message rather than watching
  nothing.
- **A loopback broker now always requires a machine token.** With no
  `--machine-token-file` / `SYNAPS_BROKER_TOKEN` it writes one to
  `~/.synaps-cli/auth-broker.token` (0600), and same-user clients pointed at
  a loopback endpoint pick it up automatically. Older clients, clients
  running as another user or with another `SYNAPS_BASE_DIR`, and
  SSH-forwarded clients get a 401 until you set `auth.machine_token` (or
  `SYNAPS_MACHINE_TOKEN`) to that token. A loopback broker also refuses
  requests whose `Host` isn't `localhost`, `127.0.0.1`, `[::1]` or its bind
  IP. `/token` no longer vends Meta Muse keys; `/proxy` still serves Muse.
- Upgraded clients follow their own `auth.account.*`. The broker host's
  selection applies only to older clients, or to clients set to `auto`.

## `synaps status`

`synaps status` has a new layout and new flags (`--provider`, `--account`,
`--all`, `--json`, `--verbose`). Scripts that parsed the old text output
should switch to `--json`.

## Extensions

- `tool.call` params now always include `session_id` (string, or `null` for
  workers). Ignore params keys you do not know.
- `on_message_complete` may return `{"action":"context_phase","phase":…}`.
  This needs `session.lifecycle` and `privacy.llm_content`. Its event `data`
  gains `context_management`.
- A JSON-RPC `error` reply is now returned to the caller as-is. The host no
  longer restarts your process and retries the call. Crash or close stdout if
  you need a restart.
- In the `before_tool_call` chain only `block` stops evaluation. A `modify`
  no longer hides the call from later extensions, and a `confirm` no longer
  skips a later `block`.

## Subagents

A worker that failed before its first history checkpoint is archived with an
empty history. `subagent_resume` now refuses such an archive (including by
`archive_path`) with the archived error, instead of starting the worker with
no context. Start a new subagent instead. 0.10.2 does not refuse these.

## TUI

- **Alt-↑/↓ and Ctrl-↑/↓ switch between subagent views.** Both are reserved
  and can no longer be bound by keybinds or plugins; Alt-↑/↓ used to fall
  through to input history (plain ↑/↓ still do). On macOS, Ctrl-↑/↓ are
  taken by Mission Control before the terminal sees them: use Alt (in
  Terminal.app, enable "Use Option as Meta key") or `/watch`.
- **Confirm prompts:** `y` allows, `n` or Esc denies, Tab or ←/→ select a
  button, and Enter presses the selected one (Deny by default). Focus no
  longer wraps, and `h`/`l` no longer move it. **"Allow all" has no letter
  key** (`a` does nothing now): select it, press Enter, then press Enter
  again to confirm. It covers only the extension that asked, only the input
  owner can arm it, and `/new` or `/confirms reset` revokes it
  (`/confirms status` shows it). Keys typed in the first 400 ms after a
  prompt appears are ignored, and each ignored key restarts that delay.
- `synaps --attach … --no-confirm-answers` stops that TUI from answering
  confirm prompts.

## Packagers

The root crate now has a default `command-exec` feature.
`--no-default-features` builds a binary without the `bash` tool and without
`shell_*` tools. In 0.10.2 that flag did nothing. **It is not a sandbox:**
`write`/`edit`, watcher `wake_if` (`sh -c`), extensions, MCP servers and
plugin commands still start processes.

The minimum supported Rust version is now 1.88 (it was declared as 1.80,
which the locked dependencies no longer build with).

## Crate users (`synaps-engine` / `synaps-core`)

- **Command execution is a feature.** `bash` and `shell_*` are behind
  `synaps-engine`'s default `command-exec` feature. If you depend on
  `synaps-tui`, or on `synaps-engine` with `default-features = false`, enable
  `synaps-engine/command-exec` to keep them.
- **Turn budgets:** `TurnBudget::max_provider_rounds`, `max_tool_calls` and
  `max_accumulated_tool_result_bytes` are `Option`s (`None` = no limit), and
  `TurnBudget` gains `max_total_tokens`. `TurnBudgetOverrides` uses
  `Option<TurnLimit<_>>` for the same three fields (`TurnLimit::Max(n)` or
  `TurnLimit::Unlimited`; `Max(0)` means none allowed).
  `TurnBudgetsConfig` gains an `event` field, which breaks struct literals.
  New enum variants `TurnRole::Event` and `BudgetDimension::TotalTokens`
  (wire label `total_tokens`) break exhaustive matches.
- **`BrokerError`** is now `#[non_exhaustive]` and has six new variants:
  `UnknownAccount`, `UnsupportedAccount`, `InvalidAccount`,
  `NoAccountAvailable`, `BrokerTooOld` and `Refresh`. Matches need a
  wildcard arm.
- `AuthConfig`, `SubagentDisplayRow`, `Welcome`, `SessionReloadRecord` and
  `ReloadState` have new public fields, which breaks struct literals.

These breaks are why the release is 0.11, not 0.10.3.
