# Upgrading from 0.12.0 to 0.13.0

**After installing, reload the daemon:** `synaps daemon reload`, then
restart attached TUIs. A reload stops running subagents (`subagent_resume`
continues them), so let them finish first. Daemon protocol (v3) and
extension protocol (1) are unchanged. What is new on the daemon socket is
announced in `Welcome.features` (`session_workers`, `session_page`,
`addressed_replies`, `prompt_outcome`, `cache_expiry`); see
[Negotiation](../daemon-mode.md#negotiation).

## Extensions: `before_message` inject is saved by default

Until 0.12.0, content a `before_message` hook injected was shown for one
request and never kept. From 0.13.0 (#425) each part is written once into
the stored conversation, on the user message the hook ran for, fenced with
the extension id. From then on it is ordinary history: later requests,
resumed sessions, rollover archives and compaction all see it.

**If your extension injects something meant for one turn only** (recall
results, status lines, anything that would pile up in history), mark it:

```json
{"action": "inject", "content": "…", "forget": true}
```

`forget` content is shown at the tail of every request of that turn, never
stored, and leaves a marker in history:
`[<extension id> context was shown here for one turn and not kept]`.
`parts` lets one result mix saved and `forget` parts. A saved part over
16 KiB is handled as `forget`.

The hook now runs once per new user message of a turn (prompt, steer, event
message), and never again for the same message (a resend or resumed turn
doesn't re-run it). Its `message`, titles, previews and search never include
saved extension context.

Hosts that support this say so with `features: ["inject.forget"]` in the
`initialize` params. `content` stays required and the protocol stays 1, so
an extension that checks the feature works against older hosts too.
Details: [protocol.md, `inject`](../extensions/protocol.md#before_message-inject-saved-by-default-forget-for-one-turn).

## `google-gemini` is removed

The Gemini Code Assist sign-in was built on Gemini CLI's internal API and
sign-in flow, which Google's terms do not permit third-party tools to use.
0.13.0 removes it (#460):

- `synaps login --provider google-gemini` (or `gemini`, `gemini-cli`,
  `gemini-code-assist`) refuses and names the replacement.
- `google-gemini/...` models no longer route.
- `SYNAPS_GOOGLE_GEMINI_CLIENT_ID` and `SYNAPS_GOOGLE_GEMINI_CLIENT_SECRET`
  are no longer read.
- A saved `google-gemini` sign-in is removed from `auth.json` at start, by
  name and without reading its value, with one log line: "removed saved
  google-gemini sign-in".

**Replacement:** a Google AI Studio API key.

```bash
synaps login --provider google   # paste the key, or pipe it on stdin
```

Then use a `google/...` model. Check `model`, `subagent_model`,
`compaction_model` and your favorites for `google-gemini/...` ids and change
them. AI Studio keys and Vertex are unchanged.

## `compaction_model`: the chat's own model by default

0.12.0 wrote compaction summaries with `claude-sonnet-4-6` unless told
otherwise, and fell back to it. 0.13.0 drops that default and that fallback
(#371):

| `compaction_model` | Who writes the summary |
|---|---|
| unset, empty or `match` (default) | the chat's own model |
| `provider-small` | the small model pinned for the chat's provider, on the chat's account (`claude-haiku-5-5` on Anthropic; the chat's own model elsewhere) |
| a model id (`claude-…` or `provider/model`) | that model |

So an Opus chat now compacts with Opus. On Anthropic with a warm cache the
summary request reads the history from the prompt cache (#461), which is
usually the cheaper request anyway. To keep the old behaviour:

```
compaction_model = claude-sonnet-4-6
```

A named or pinned model that can't be used (no route, no credential, a
smaller context window than the chat's, a reasoning level its provider
refuses) gives way to the chat's own model, and the compaction line says
so. Any other value warns at load and is `match`.

## Daemon clients

### Replies reach only the client that asked

Every client numbers its own requests, so two clients' request 5 share an
id. 0.12.0 broadcast every reply; 0.13.0 (#448, feature
`addressed_replies`) addresses them:

- `QueryResult` (queries, engine and plugin command replies, resume
  errors, close/rename/checkpoint replies) and `AnswerRefused` reach only
  the attachment that asked. A reply to the host reaches no client.
- `SettingChanged` and `Resumed` are shared state and still reach every
  client, but all except the asker see the id `VIEW_CHANGED_SETTING_ID`
  ("answers no request of yours").

The wire is unchanged. **A client that read another client's replies off
the shared stream** (an observer waiting for the driver's `QueryResult`,
say) stops receiving them and has to send its own request. See
[Request ids and replies](../daemon-mode.md#request-ids-and-replies).

### Session ids have 8 random hex characters

New ids look like `20261117-015328-1f2e3d4c` (was `…-1f2e`). They still
start with the UTC time they were made and sort by it. Ids with 4 stay
valid everywhere. A script or client that matches exactly 4 hex characters
should accept 4 or more.

### `synaps daemon sessions --json`

The output is each session as the daemon sent it, not as this build decoded
it:

- keys are in alphabetical order;
- fields an older daemon doesn't send are left out, not filled with
  defaults;
- fields this or a newer daemon adds are kept, e.g. `workers` (a session's
  background workers, present only when it has some).

Field meanings that changed with it:

- `created_at` is when the session's conversation began (kept across
  compaction and reload, moved by `/clear` and in-session `/resume`), not
  when the session was created.
- `title` is the saved row's title: the header title, else the first
  message a person typed, on one line, up to 120 characters.
- `journal_id`, not `id`, names the conversation; they differ after
  `/clear`, `/resume` and compaction.

## Credential broker

Upgrade a `synaps auth-broker` and its clients together. A 429 on one
model's own limit now cools only that model on that account (#413); an
older client reports it as the whole account's, and an older broker ignores
the model in a newer client's report and cools the whole account.

## Going back to 0.12.0

Nothing in 0.13.0 needs a migration, and 0.12.0 reads its sessions,
8-hex ids included. Expect:

- extension context saved by 0.13.0: in journal mode 0.12.0 skips the
  record that saved it, so that context is lost (never the rest of the
  history); in a stored snapshot it stays and reads as the user's own text,
  also after coming back to 0.13.0 if 0.12.0 saved the session;
- a removed `google-gemini` sign-in is not restored; sign in again on
  0.12.0 if you need it;
- `compaction_model` unset means `claude-sonnet-4-6` again.
