Cloud OAuth Providers

Implementation plan · engplan/1 · branch feat/cloud-oauth-providers

Objective and fixed decisions

Add typed azure-openai, aws-bedrock, and google-vertex providers using broker-owned credentials, dynamic catalogs, brokered runtime calls, and TUI /models. Azure v1 is Azure OpenAI only; Azure Foundry is deferred. AWS uses IAM Identity Center OIDC to obtain role credentials and broker-side SigV4 for Bedrock—not bearer OAuth. Vertex uses installed-app S256 PKCE and public regional Vertex APIs.

Feasibility gate: Synaps-owned Microsoft public-client and Google Desktop OAuth registrations are external prerequisites. Configurable broker-owned client IDs may be supported, but Azure/Vertex must not be described as deployable until registrations and live tests exist.

C0 — Feasibility and ownership

Record Microsoft and Google registration status, AWS sandbox/SSO/Bedrock prerequisites, least-privilege owners, budget/cleanup owner, and file ownership. Missing Microsoft/Google registration permits fixture-driven implementation but blocks deployment claims. Approve exact host/path/scope boundaries.

Evidence: prerequisite matrix, assigned owners, no copied first-party client IDs, clean baseline.

T1 — Typed identity, configuration, and storage

Add canonical provider descriptors and aliases-at-parse-only; separate non-secret context from secret credential state; add typed registration-required and login-required outcomes; preserve unknown auth metadata with atomic restrictive writes.

  • Azure: tenant/subscription/resource group/resource.
  • AWS: SSO start/issuer URL, SSO region, account, role, Bedrock region.
  • Vertex: project/location and configured public desktop client ID.

Acceptance: malformed context fails pre-network; secret types redact Debug; runtime/TUI wire types cannot contain refresh tokens, AWS keys, or dynamic OIDC secret.

Owner/files: Auth owner — crates/agent-core/src/core/auth/{provider,providers,storage,broker}.rs and new provider modules.

T2 — Login and refresh state machines

Azure device code uses tenant-specific endpoints, ARM https://management.azure.com/.default, and separate inference https://cognitiveservices.azure.com/.default. AWS implements RegisterClient, StartDeviceAuthorization, CreateToken, ListAccounts, ListAccountRoles, and GetRoleCredentials. Vertex implements loopback installed-app auth with exact state, S256 PKCE, cloud-platform scope, offline access, and refresh preservation.

Acceptance: intervals/slow-down/expiry/denial/cancellation; explicit AWS selection; refresh rotation; exact callback; redirect-off; atomically validated login; secret-safe output.

Verification: focused core auth tests plus storage fault/redaction tests.

Depends on: T1.

C1 — Authentication security boundary

Security review freezes provider identities, scopes/audiences, callback behavior, AWS dynamic registration handling, credential storage, redaction, host allowlists, and typed broker boundaries. Failures block runtime work until corrected; checkpoint evidence records commit, commands, owner, UTC timestamp, and result.

T3 — Dynamic catalog contracts

Azure discovers callable deployed models through ARM; AWS signs ListFoundationModels; Vertex lists regional publishers/google/models. Normalize opaque, namespaced model IDs and capabilities. Bound pagination, entries, bodies, time, concurrency, and cancellation. Cache last-known-good entries with TTL and visible stale state; never replace permission/empty results with guessed availability.

Acceptance: deduplication, pagination-loop defense, endpoint validation, separate Azure token caches, AWS expiry, Vertex project/location confinement, and unknown-model fail-closed tests.

Owner/files: Runtime owner — crates/agent-engine/src/runtime/** and catalog modules.

Depends on: C1.

T4 — Brokered runtime adapters

Implement Azure deployed-model streaming, AWS SigV4 Converse/ConverseStream, and Vertex public streamGenerateContent SSE. Broker constructs fixed authority/path/auth/signing inputs. Normalize text, tools, usage, errors, cancellation, and exactly one terminal event.

Acceptance: deterministic SigV4 vectors including session token/body; fragmented SSE/event-stream fixtures; unsupported blocks explicit; no caller URL/auth/signature injection; no token/key egress.

Owner: Runtime owner. Depends on: T3.

T5 — Zero-network unattended harnesses

Harness owner adds local fake Microsoft/AWS/Google authorities, injected clock/browser/callback/DNS/signer/storage, and a connector that fails every non-loopback socket. Cover success and adversarial polling, replay, rotation, pagination, malformed/oversized data, redirect/SSRF, storage faults, concurrent refresh, stream fragmentation, cancellation, redaction canaries, and broker/RPC credential boundaries.

Expected tests: tests/azure_openai_oauth_e2e.rs, tests/aws_bedrock_sso_e2e.rs, tests/google_vertex_oauth_e2e.rs plus focused unit suites. Default CI performs zero real network calls.

Depends on: frozen C1 interfaces; runs continuously through T3/T4.

C2 — Zero-network vertical slices

Each provider proves setup/login → catalog → one streaming request → refresh/logout entirely against fakes while external networking is denied. Security canaries have zero output hits. Existing OAuth/static provider regressions pass.

T6 — TUI /models

Group dynamic catalogs by provider; show non-secret resource/account/project and region/location context; implement loading, registration-required, login-required, permission, empty, stale, retry, filter, stable focus, and cancellation states. Selection maps exactly to a broker route.

Acceptance: no TUI auth-file/cloud HTTP access; duplicate and unknown IDs rejected; harness snapshots cover every state; deferred providers are labeled honestly.

Owner/files: TUI owner — crates/agent-tui/src/tui/models/** and minimal command/view-model wiring. Depends on: T3.

C3 — Unattended holdout readiness

All focused auth/catalog/runtime/TUI suites pass with zero external socket attempts, adversarial cases green, redaction verified, and architecture review confirming broker-only credentials.

T7 — Required live AWS validation

In a least-privilege budget-capped sandbox: device login; explicit account/role selection; role credential acquisition; ListFoundationModels; one harmless Converse; one short/cancelled ConverseStream; expiry refresh; CloudTrail review; logout/cache clearing. Record only commit, timestamp, regions, model ID, actions and result—no credentials or response content.

Acceptance: SigV4 with session credentials, no bearer inference, only expected principals/actions/hosts, bounded spend, clean logout. Any secret leak or unexpected action is a blocker.

Owner: Release owner with Security reviewer. Depends on: C3.

T8 — Deferred Azure and Vertex live validation

Azure: after Synaps Microsoft registration, consent and sandbox deployment exist, verify ARM deployment discovery and one streamed Azure OpenAI inference with distinct audiences. Foundry remains prohibited. Vertex: after Synaps Google Desktop registration, consent/test-user and billed sandbox exist, verify publisher discovery and one public SSE inference. Deferred means not waived and not generally available.

Owner: Release owner. Depends on: external prerequisites and C3.

T9 — Final verification and convergence

Freeze candidate, run fmt check, workspace tests, workspace check, and release build sequentially. Run weighted holdout with threshold 0.90 and at most 10 total evaluator calls. Apply at most 2 diagnosed fix iterations, rerunning affected and full gates; never weaken tests or waive security/feasibility gates.

Commands: cargo fmt --all -- --check; cargo test --workspace -- --test-threads=1; cargo check --workspace; cargo build --release, each with CARGO_BUILD_JOBS=8.

Depends on: T6, T7; T8 gates only Azure/Vertex availability.

C4 — Release candidate

Requires weighted holdout ≥0.90, acceptable security axis, AWS live evidence, clean worktree, reproducible zero-network tests, synchronized docs, and provider flags that keep Azure/Vertex off except approved sandboxes until their live gates pass. Canary AWS, monitor secret-safe auth/signing/latency/cancellation/spend metrics, then expand. Rollback disables login/catalog/runtime and clears broker cache without exporting credentials.
